# 카카오톡 ‘코스 보기’ 홈 이동 진단

> **후속 9/12 13:30 KST:** 공유 수정과 회귀 테스트 두 파일만 커밋(`075b160`)·푸시했고 Vercel 배포 성공 및 운영 JS의 전체 주소 변환을 확인했다. 기존 코스 HTML/API도 200이다. 새 메시지의 iPhone 클릭 확인은 남아 있다. [수정·배포 결과](2026-09-12-카카오공유-수정-배포결과.md). 아래 HEAD/운영 미반영·진단만 수행 등의 기술은 배포 전 조사 당시 기록이다.

2026-09-11 23:31 KST 정리. 사용자 신고: 카카오톡으로 공유한 메시지의 ‘코스 보기’를 누르면 홈으로 이동한다.

## 결론

**운영 공유 코드에 절대 주소 변환 수정이 반영되지 않은 것을 확인했다.** 운영 코드는 전달받은 shareUrl을 카카오의 콘텐츠/버튼 링크 및 클립보드에 그대로 넣고 있다. 로컬에는 이전 작업에서 `new URL(shareUrl, window.location.origin).href`로 변환하는 수정이 이미 있다.

**후속 실제 코스 확인:** 사용자가 기존 코스의 전체 URL을 제공하고, URL을 직접 보내면 정상적으로 열리지만 카카오 공유 버튼으로 만든 메시지는 실패한다고 확인했다. 해당 페이지와 공유 조회 API를 각각 1회 직접 요청해 모두 HTTP 200, 페이지 최종 URL 유지, 코스 데이터 존재를 확인했다. API의 shareUrl은 `/course/{slug}` 상대 경로였고 응답 최상위에 editToken/edit_token 필드는 없었다. 공개 문서에는 해당 코스의 실제 slug·제목·장소·내용을 기록하지 않는다.

이 표본은 **서버의 코스 조회는 정상이고, 운영 공유 코드가 상대 경로를 외부 메시지 링크로 전달하는 결함이 남아 있음**을 보여준다. DB 익명 권한 복원은 해결책이 아니다. 문제가 난 카카오 메시지 내부의 실제 링크/리다이렉트와 Kakao 제품 링크 설정은 직접 검사하지 않았으므로, 수정본 배포 후 새 메시지를 통한 최종 동작 확인은 남아 있다.

## 근거

1. 현재 생성/조회 API의 shareUrl 형식은 `/course/{slug}`다. HEAD의 SaveShareBar는 이 상대 경로를 콘텐츠 링크·‘코스 보기’ 버튼 링크·복사 주소에 그대로 전달한다.
2. 운영 공개 HTML에서 확인한 코스 청크 `/_next/static/chunks/16j3uxhrkvijs.js`를 읽었다. 공유 호출은 `mobileWebUrl:e,webUrl:e`, 복사는 `clipboard.writeText(e)`이며 해당 청크에 `new URL(` 변환이 없다. 로컬 공유 변경이 반영되지 않은 구 코드와 일치한다. 운영 소스 전체의 커밋/배포 ID까지 식별한 것은 아니다.
3. 존재하지 않는 고정 진단 경로 `/course/__codex_missing_course_probe__`의 HTML 응답은 HTTP 200, 최종 경로도 동일했다. HTTP 단계에서 홈 리다이렉트는 없었다. 이 응답의 200은 실제 코스 조회 성공이 아니며 클라이언트 렌더 완료를 검증한 것도 아니다.
4. HEAD·로컬 코스 결과 컴포넌트의 조회 실패 처리는 ‘코스를 찾을 수 없어요’다. 홈 자동 이동 로직은 확인되지 않았다. 미들웨어는 인증 세션 갱신이며 공유 페이지를 홈으로 보내는 분기가 없다. OAuth 콜백의 홈 이동은 별도 경로이므로 실제 링크가 그 경로를 거치는지 확인이 필요하다.

카카오 기본 템플릿의 모바일/웹 링크는 등록된 도메인과 일치해야 한다. 도메인이 없는 상대 경로를 넘기는 현재 운영 방식은 이 계약에 맞지 않는다. [기본 템플릿 공식 문서](https://developers.kakao.com/docs/ko/message-template/default#link)

제품 링크용 웹 도메인 설정과 JavaScript SDK 도메인 등록은 별개다. 소유자가 사용하는 Kakao 앱의 제품 링크 관리에도 운영 도메인이 등록돼 있는지 확인할 수 있으나, 이번 진단에서는 설정을 조회·변경하지 않았다. [앱 설정 공식 문서](https://developers.kakao.com/docs/ko/app-setting/app#product-link)

## 외부 전송 없는 비교 검증

TypeScript로 HEAD/로컬 SaveShareBar를 메모리에서 변환하고, React 훅·UI 요소·Kakao·클립보드·fetch·타이머를 모두 모킹해 두 버튼의 실제 핸들러를 호출했다. 임의의 합성 코스 경로만 사용했다.

| 같은 입력 `/course/qa-share-link` | HEAD | 로컬 |
|---|---|---|
| 콘텐츠 mobileWebUrl / webUrl | 상대 경로 유지 | `https://emochu.vercel.app/course/qa-share-link` |
| ‘코스 보기’ mobileWebUrl / webUrl | 상대 경로 유지 | 같은 전체 주소 |
| 링크 복사 | 상대 경로 유지 | 같은 전체 주소 |

두 버전 각각 5개 주소 대상의 기대값을 확인했다. 카카오 메시지 전송·실제 클립보드 변경·보관 API 호출은 없었으며 fetch는 모킹했다. 카카오 서버의 URL 처리나 iPhone 인앱 브라우저를 재현한 검사는 아니다.

## 다음 조치

- 사용자 제공 전체 코스 URL의 직접 조회 확인은 완료했다(페이지/API 200). 동일 URL을 다시 요청하거나 같은 표본의 DB 조회를 반복하지 않는다. 실제 카카오 메시지 클릭 성공은 배포 후 확인한다. 토큰·키 값은 받지 않는다.
- 해당 표본은 실제 코스 조회 정상/카카오 공유 메시지 실패로 구분됐다. 기존 로컬 절대 주소 변환을 운영에 반영하는 것이 우선이다. DB 익명 권한은 다시 열지 않는다.
- 운영 배포 대상·범위·되돌릴 배포를 확인하고 승인받아 기존 절대 주소 수정본을 반영한다. 누적 미커밋 변경 전체를 자동 게시하지 않는다.
- 배포 후 기존 저장 코스 화면을 새로고침하고 **새 공유 메시지**로 확인한다. 이미 보낸 메시지의 잘못된 URL이 앱 코드 배포만으로 교정된다고 가정하지 않는다. 새 AI 코스를 생성할 필요는 없다.

이번 작업은 진단과 문서 정리만 수행했다. 앱 소스·DB 권한·Kakao 설정·운영 배포는 변경하지 않았다. 직접 실행한 운영 GET은 홈 HTML 1회, 고정 미존재 코스 경로 HTML 1회, 해당 페이지에서 찾은 공개 JS 1회다. 첫 홈 GET은 샌드박스 네트워크 차단 후 승인된 읽기 요청으로 전환했다. 미존재 페이지의 메타데이터 렌더는 서버 내부의 미존재 코스 API 조회를 유발할 수 있다. 실제 사용자 코스·편집 토큰은 조회하지 않았으며 AI·관광 API를 직접 호출하지 않았다. 전체 게이트는 재실행하지 않았고 최신 기록은 22:18의 516 tests GREEN이다.

후속 URL 제공 후에는 사용자 지정 코스의 HTML 1회·공유 조회 API 1회를 추가로 읽었다. 최초 샌드박스 접속은 차단됐고, 승인된 읽기 요청으로 확인했다. API에는 일반 조회수 증가가 있으므로 완전 무변경 DB 조회라고 표현하지 않는다(페이지 메타데이터 조회도 발생할 수 있음). 코스 내용·좌표·토큰 값은 출력/파일에 보관하지 않았다. 메시지 발송·생성·편집·코드 변경·커밋·푸시·배포·DB 권한 변경은 하지 않았으며 이 후속에서도 전체 게이트를 다시 실행하지 않았다.
