> 인수인계 P1 의 착수 순서 1 = **"먼저 측정부터 한다"**. 그 측정을 끝냈다.
> 방법: ① 응답 헤더 `x-emochu-timings` 추가 배포(`e8255a1`) ② 운영에 **8회 생성**(조건을 갈라서) ③ Gemini 모델별 직접 측정.
> 🔴 결론부터: **대기시간 문제가 아니라 「AI 코스가 안 만들어지는」 문제다. 8회 중 5회가 규칙 폴백이었다.**

## 1. 측정 방법

`app/api/course/route.ts` 는 단계별 소요를 로그로 남기지만, **서버 로그를 열 수 없는 쪽은 총 소요시간밖에 못 본다.**
그래서 같은 요약을 응답 헤더로도 실었다(`e8255a1`). 본문 계약은 그대로다.

```
x-emochu-timings: total=53623 ai=48716 collect=2769 persist=876 enrich=66 finalize=4 score=1
                  candidates:80 festivals:6 ai:gemini stops:6 persistence:saved
```

단계는 `이름=ms`, 부가 정보는 `이름:값`. 2026-09-21 18:30~18:40 KST, 운영(`emochu.vercel.app`)에 **순차 8회**(25초 간격, 429 시 즉시 중단 규칙 — 발동 안 함).

## 3. 원인 (모델별 직접 측정으로 확정)

실제 코스와 같은 크기(입력 약 6,300토큰, 후보 80개)로 모델마다 1회씩 직접 호출했다.

| 모델 | 결과 | 소요 |
|---|---|---|
| `gemini-3.6-flash` (1순위) | 🔴 **503 UNAVAILABLE** — *"currently experiencing high demand"* | 6.6초 |
| `gemini-3.5-flash` (2순위) | 🔴 **503 UNAVAILABLE** — 같은 사유 | 1.2초 |
| `gemini-2.5-flash` (3순위) | ✅ 200 · 6곳 JSON 정상(출력 1,252토큰) | **48.6초** |

> 참고: **8토큰짜리 최소 요청**은 세 모델 다 200 이었다(3.6 은 5.6초, 나머지 0.8초).
> 즉 키·권한 문제가 아니라 **실제 크기 요청에서만 503** 이 난다.

### 시간이 어떻게 53초를 넘는가

`lib/weekend-ai.ts:1415` 의 재시도 정책은 **503 → 3초 대기 → 같은 모델 재시도 → 또 503 → 다음 모델** 이다.

```
3.6-flash  503(6.6s) + 3초 대기 + 503 재시도(6.6s) ≈ 16초
3.5-flash  503(1.2s) + 3초 대기 + 503 재시도(1.2s) ≈  6초
2.5-flash  200 이지만 48.6초  → 시작 시점에 남은 예산이 30초 남짓
────────────────────────────────────────────────
합계 ≈ 70초  ≫  AI 예산 53초  → timeout_fallback
```

관측된 53~55초 클램프와 정확히 맞는다. **코드 주석(`weekend-ai.ts:118-125`)이 8/19 에 이미 같은 현상을 적어 뒀다** — 그때는 3.5 가 503 이라 3.6 으로 1순위를 옮겼는데, 지금은 **둘 다** 503 이다.

## 4. 무엇이 문제인가

- 심사위원이 지금 써보면 **10번 중 6번은 「AI 맞춤 일정」이 아니라 「규칙 기반 기본 일정」**을 받는다. 그것도 **54초 기다린 뒤에**.
- 폴백 코스도 성립은 한다(장소 3~9곳, 구간 0.2~2.3km). 하지만 **식사 보완·이야기·팁 같은 AI 산출물이 없고**, 화면에도 `규칙 기반 기본 일정` 으로 표시된다.
- 완성도(30점)·실용성(25점) 두 축에 동시에 걸린다.

## 7. 한계

- **표본 8회, 한 시간대(18:30~18:40 KST)**다. Gemini 503 은 시간대에 따라 바뀐다 — 다른 시간엔 폴백률이 다를 수 있다.
- 모델별 측정은 **로컬 키**로 했다. 운영 키와 같은지는 확인하지 않았다(503 은 모델 쪽 사유라 키와 무관하지만, 429 라면 달라진다).
- 서버 로그(`[이모추AI] … 서버 과부하 → 3초 후 재시도`)는 이 세션에서 읽지 못했다. **Vercel 대시보드 > Logs 에서 `이모추AI` 로 검색하면** 위 추정(재시도 횟수·모델별 실패 사유)을 그대로 교차 검증할 수 있다.
- 오늘 생성 사용량: **9회**(오후 종단 1 + 이번 8). 개인 일일 상한 기본값 20 기준으로 11회 남았다.
