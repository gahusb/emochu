## 3. 원인 (모델별 직접 측정으로 확정)

실제 코스와 같은 크기(입력 약 6,300토큰, 후보 80개)로 모델마다 1회씩 직접 호출했다.

| 모델 | 결과 | 소요 |
|---|---|---|
| `gemini-3.6-flash` (1순위) | 🔴 **503 UNAVAILABLE** — *"currently experiencing high demand"* | 6.6초 |
| `gemini-3.5-flash` (2순위) | 🔴 **503 UNAVAILABLE** — 같은 사유 | 1.2초 |
| `gemini-2.5-flash` (3순위) | ✅ 200 · 6곳 JSON 정상(출력 1,252토큰) | **48.6초** |

> 참고: **8토큰짜리 최소 요청**은 세 모델 다 200 이었다(3.6 은 5.6초, 나머지 0.8초).
> 즉 키·권한 문제가 아니라 **실제 크기 요청에서만 503** 이 난다.

### 시간이 어떻게 53초를 넘는가

`lib/weekend-ai.ts:1415` 의 재시도 정책은 **503 → 3초 대기 → 같은 모델 재시도 → 또 503 → 다음 모델** 이다.

```
3.6-flash  503(6.6s) + 3초 대기 + 503 재시도(6.6s) ≈ 16초
3.5-flash  503(1.2s) + 3초 대기 + 503 재시도(1.2s) ≈  6초
2.5-flash  200 이지만 48.6초  → 시작 시점에 남은 예산이 30초 남짓
────────────────────────────────────────────────
합계 ≈ 70초  ≫  AI 예산 53초  → timeout_fallback
```

관측된 53~55초 클램프와 정확히 맞는다. **코드 주석(`weekend-ai.ts:118-125`)이 8/19 에 이미 같은 현상을 적어 뒀다** — 그때는 3.5 가 503 이라 3.6 으로 1순위를 옮겼는데, 지금은 **둘 다** 503 이다.

## 9. 🔴 정정 — 「폴백 0/8」은 틀렸다 (2026-09-22 13:10)

사용자가 *"확인해봤어?"* 라고 물어 **실제 화면으로** 종단 확인을 했고, 거기서 8절의 오독이 드러났다.

### 무슨 일이 있었나

위저드로 코스를 만들었더니 응답 헤더는 `ai:gemini` 인데 **화면은 「규칙 기반 기본 일정」**이었다.

```
헤더 : total=35800 ai=29764 ... ai:gemini stops:5 persistence:saved
화면 : AI 연결이 원활하지 않아 관광정보를 기반으로 정리한 기본 일정이에요. / 규칙 기반 기본 일정
```

원인은 계측의 구멍이다. 헤더의 `ai:` 는 **라우트가 타임아웃 경주에 걸렸는가**만 말한다.
엔진(`generateCourse`)이 모델 실패·검증 실패로 **안에서** 폴백하면 `ai:gemini` 인 채로 규칙 코스가 나간다.

### 다시 센 결과

응답 본문의 `generationMode` 로 다시 세면:

| 측정 | 헤더 `ai:` 기준(내가 보고했던 값) | **실제 `generationMode` 기준** |
|---|---|---|
| 9/21 18:30 (수정 전) | 폴백 5/8 | **폴백 5/8** (일치) |
| 9/22 05:30 (수정 후) | 폴백 **0/8** ❌ | **폴백 1/8** ✅ |

**즉 「5/8 → 0/8」이 아니라 「5/8 → 1/8」이다.** 개선은 여전히 사실이지만 폭이 다르다.
9/21 측정은 두 기준이 우연히 일치해서(전부 타임아웃 폴백) 오독이 드러나지 않았다.

### 막은 방법

헤더에 `mode:` 를 실었다(`abce82c`, 570 tests GREEN). 검사 2개가 이 구멍을 고정한다.
배포 후 확인: `... ai:gemini stops:6 persistence:saved mode:ai` — 본문 `generationMode` 와 일치.

🔴 **다음 사람에게**: 폴백률을 셀 때는 `mode:` 를 봐라. `ai:` 는 경주 결과일 뿐이다.
