# 9/11 DB 권한 확인·보완 적용안

상태: **사용자의 017 실행 성공 보고 후, 9/11 23:20 KST 운영 메타데이터에서 목표 권한 차단 상태 확인. 실제 서비스 회귀 확인·기존 토큰 처리·앱 배포는 별도 미완료.**

## 최신 확인 — 017 실행 후

사용자는 017 실행 후 `Success. No rows returned.`를 보고했고, 이어 갱신된 점검문의 결과를 첨부했다. 점검 시각은 `2026-09-11T14:20:44.289291+00:00`(**한국 시간 23:20:44**)이다. 다음은 사용자 제공 메타데이터를 대조한 결과이며 에이전트가 운영 DB에 직접 접속해 SQL을 실행한 것은 아니다.

| 확인 항목 | 결과 |
|---|---|
| anon/authenticated × 코스·공개 뷰·사용량 3개 객체 | 테이블 CRUD·열 SELECT/INSERT/UPDATE/REFERENCES 모두 false |
| wk_courses.edit_token SELECT | anon/authenticated false, service_role true |
| 사용량 함수 EXECUTE | anon/authenticated false, service_role true |
| 서버 역할 | 3개 객체 CRUD 유지, BYPASSRLS true, superuser false |
| 일반 클라이언트 역할 | BYPASSRLS false, superuser false |
| RLS·정책 | 두 테이블 RLS true, policies 빈 배열로 공개 SELECT 정책 제거 확인 |

9개 역할/객체 조합이 빠짐없이 있고 기대 권한·역할·RLS·함수 상태와 불일치가 없음을 확인했다. 뷰는 `kind: v`, 소유자 postgres, options null이며 클라이언트 권한은 차단됐다. 뷰의 RLS false와 edit_token 컬럼이 없는 두 객체의 null은 오류가 아니다.

**이번 대상의 DB 직접 접근 차단 확인은 완료했다. 017을 다시 실행할 필요는 없다.** 현재 서버 키의 실제 프로젝트 일치·배포 버전, 기존 공유 코스 조회·로그인 내 코스·정상 편집 같은 운영 앱 동작은 이 메타데이터만으로 확인할 수 없다. 또한 과거 유출/변조 여부·기존 토큰 폐기 여부·코스 데이터 보존 자체는 행을 조회하지 않았으므로 별도 미확인이다. 기존 토큰 무효화와 다른 DB 경로의 보안까지 완료된 것으로 해석하지 않는다.

다음은 새 AI 생성 없이 기존 공유 링크와 로그인 내 코스 목록을 확인한다. 이후 동의한 테스트 코스의 생성자 편집/방문자 편집 거부를 검증한다. 현재 작업은 문서 상태만 갱신했으며 코드 변경·게이트 재실행·운영 호출·배포·토큰 교체는 하지 않았다. 기존 게이트는 22:18의 516 tests GREEN이다.

## 1. 최초 점검 — 변경 전 22:05 기록

사용자가 전달한 점검 시각은 `2026-09-11T13:05:37.711988+00:00`(한국 시간 22:05:37)이다. 이 작업에서 운영 DB에 직접 연결하거나 실제 코스·토큰 행을 조회하지 않았다.

| 대상 | 사용자 제공 결과 | 판정 |
|---|---|---|
| `wk_courses` | anon/authenticated SELECT 및 edit_token SELECT = true, RLS 활성, PUBLIC 대상 `public_read_courses` SELECT USING(true) | DB 권한상 모든 코스 행의 편집 토큰 조회를 허용하는 구성. 배포 전 우선 차단 대상 |
| `wk_courses_public` | anon/authenticated SELECT·INSERT·UPDATE·DELETE = true, edit_token 컬럼 없음 | 뷰가 원본 테이블 접근을 차단하지 않음. 소유자/옵션은 당시 결과에 없어 운영 쓰기 우회 여부는 추가 확인 필요 |
| `wk_usage` | anon/authenticated DML grant = true, RLS 활성, 정책 없음 | grant만으로 행 접근을 확정할 수 없음. 일반 클라이언트는 정책 없는 RLS로 행 접근이 차단되는 구성 |
| `service_role` | 3개 객체 모두 CRUD grant = true | 서버 사용에 필요한 객체 권한은 있음. 운영 서버 키 설정·역할의 BYPASSRLS는 별도 확인 |

`rls_forced: false` 자체를 취약점으로 판정하지 않는다. 뷰의 `rls_enabled: false`도 테이블과 같은 방식으로 해석하지 않는다. `edit_token_select: null`은 뷰/사용량 테이블에 그 컬럼이 없다는 뜻이지 차단 확인이 아니다.

객체 권한과 RLS는 함께 판단해야 한다. 뷰는 소유자 권한으로 동작할 수 있어 원본 테이블의 RLS만으로 안전을 보장할 수 없다. [Supabase 공식 설명](https://supabase.com/docs/guides/database/postgres/row-level-security)

**실제 외부 유출·악용·변조를 확인한 것은 아니다.** Data API의 노출 스키마 설정, 뷰 소유자/옵션, 외부 조회 이력, 과거 영향 기간은 이번 결과에 없다. 다만 편집 토큰을 인증 수단으로 쓰는 현재 앱에서 이 DB 구성은 그대로 두면 안 된다.

## 2. 로컬 수정 범위

- [017 마이그레이션](../supabase/migrations/017_lock_down_course_access.sql): `PUBLIC`, `anon`, `authenticated`의 코스 테이블·공개 뷰·사용량 테이블 권한과 `wk_bump_usage(date,text)` 실행 권한 회수. 공개 SELECT 정책 제거, 테이블 RLS 유지, service_role CRUD/RPC 권한 명시.
- 기존 행·공유 slug·편집 토큰·공개 동의·사용량 카운터는 변경하지 않는다. 테이블/뷰 삭제, 다른 테이블 권한, 스키마 전체 기본 권한, 역할 멤버십 변경도 없다.
- 선행 객체/역할 누락, 서비스 역할의 RLS 우회 권한 부재, 잔존 상속 권한, 서버 권한 보존 실패 시 전체 트랜잭션 중단. 5초 잠금 대기 제한. 의존 권한을 무차별 회수하는 CASCADE는 사용하지 않는다.
- [admin 클라이언트](../lib/supabase/admin.ts): 서버 키/URL 누락·공백 또는 공개 anon 키를 서버 키로 복사한 설정이면 SDK 호출 전 중단한다. anon 폴백 제거, 오류에 실제 값 포함 안 함. 이것만으로 다른 프로젝트 키·유효성·JWT 역할까지 검증되지는 않는다.
- [읽기 전용 점검문](../scripts/check-course-access.sql): 기존 결과에 역할 BYPASSRLS, 객체 종류·소유자·옵션, 열 권한, 해당 사용량 함수 EXECUTE 메타데이터를 추가했다. 함수 실행이나 코스·사용자 행 조회는 하지 않는다.

PostgreSQL의 테이블 REVOKE는 같은 역할의 해당 열 권한도 회수한다. 다른 역할에서 상속된 권한은 남을 수 있어 SQL 후조건에서 열 권한까지 별도로 검사한다. [PostgreSQL REVOKE 문서](https://www.postgresql.org/docs/current/sql-revoke.html)

기존 012~016 파일은 적용 이력으로 보존했다. 그 안의 “공개 정책 유지” 주석은 017 이후의 권고가 아니다. 초기 테이블용 010 파일은 현재 저장소에 없으므로 과거 번호만 보고 전체 마이그레이션을 다시 실행하지 않는다.

## 3. 로컬 검증

[권한 회귀 스크립트](../scripts/verify-course-access.mjs)는 **PGlite 0.5.8 / PostgreSQL 18.3 WASM**의 매번 새 메모리 DB에서 실행했다. 기본 테이블은 합성 fixture, 011~017은 저장소 원문이다. 실제 사용자 행·환경변수·운영 접속 주소를 사용하지 않았다. PGlite는 PostgreSQL의 WASM 빌드다. [공식 소개](https://pglite.dev/docs/about)

SQL 검사 **14개 통과**(집계상 부모 검사 1개 포함; 독립적인 운영 표본 14건이 아님):

- 변경 전 anon/authenticated의 합성 편집 토큰 조회 재현.
- 변경 전 사용량 RLS 차단, 원본 코스 UPDATE 차단과 기본 소유자 권한 뷰의 UPDATE 허용을 구분. **이 뷰 쓰기 재현을 운영 환경에서의 성공으로 표현하지 않는다.**
- 변경 후 두 클라이언트 역할 × 3개 객체 × SELECT/INSERT/UPDATE/DELETE = **24개 쿼리 거부**, 토큰 열 조회와 사용량 함수 실행도 거부.
- PUBLIC/열 단위 권한 제거, 서버 역할의 공유 SELECT·생성·수정·보관/공개 토글·삭제·사용량 함수 증가 확인. 이는 SQL 수준 검사이지 운영 앱 종단간 통과가 아니다.
- 행/토큰/slug/기존 카운터 보존, 재실행 동일 결과, 상속 테이블·열·함수 권한 잔존 시 롤백, 서버 BYPASSRLS/함수 누락 시 롤백, 대상 없는 메타데이터의 null 처리 확인.
- 서버 설정 단위 검사 8개와 공유 조회 허용 컬럼/민감 필드 비노출 검사 1개 추가. 기존 포함 해당 두 파일 14개 통과. 전체 게이트 결과는 아래 기록한다.

## 4. 운영 적용 순서 — 소유자 확인/승인 후

**사용자 확인 이력:** 먼저 Vercel Production의 `SUPABASE_SERVICE_ROLE_KEY`가 설정되어 있다는 답변을 받았다. 이후 사용자의 017 실행 성공 보고와 23:20 메타데이터로 목표 권한 상태를 확인했다. 키 값·유효성·프로젝트 일치·현재 운영 버전은 직접 검증하지 않았다. 키 값은 요청하거나 조회하지 않았다. 아래 적용 절차는 이력/운영 참고용이며 현재 대상에 017 재실행을 요청하는 것이 아니다.

1. **먼저 서버 설정 확인.** Vercel의 해당 프로젝트 **Production**에 `SUPABASE_SERVICE_ROLE_KEY`가 설정되어 있고, `NEXT_PUBLIC_SUPABASE_URL`과 같은 Supabase 프로젝트의 서버 키인지 소유자가 확인한다. 키 값은 채팅·캡처·보고서에 보내지 않는다. 로컬 .env나 Preview의 값이 있다고 Production도 같다고 가정하지 않는다.
2. 현재 운영 코스 조회·저장·편집·내 코스 경로가 서버 admin 클라이언트를 사용하는 버전인지 확인한다. 배포 ID/커밋·필요한 변경 범위를 확인한다. 키 누락이나 운영 코드 차이가 있으면 설정/코드의 별도 승인·배포 후 진행한다. 공개 조회 권한을 다시 넓혀 우회하지 않는다.
3. 갱신된 읽기 전용 점검문으로 객체·뷰 옵션·함수·역할 상태를 재확인하고, 기존 공유 링크 1개를 소유자가 정상 조회할 수 있는지 확인한다. 새 AI 생성은 하지 않는다. 백업/복구 지점과 작업 시각·대상 프로젝트를 기록한다.
4. 권한 변경을 승인한 소유자가 **017 파일 전체만** Supabase SQL Editor에서 한 번 실행한다. 기존 012~016을 다시 실행하지 않는다. 부분 선택 실행은 하지 않는다. 오류가 나면 추가 변경하지 말고 오류 내용을 확인한다. 같은 세션이 실패한 트랜잭션 상태이면 `ROLLBACK;`으로 종료한다.
5. 갱신된 `check-course-access.sql`을 재실행한다. 아래 기대값과 비교하고 **메타데이터 결과만** 공유한다. 완료 시각도 기록한다.
6. 기존 공유 링크 읽기, 로그인 내 코스 읽기를 우선 확인한다. 소유자 동의하에 별도 테스트 코스에서 정상 토큰 편집 성공·방문자 편집 거부·보관을 확인한다. 커뮤니티 공개는 테스트 명목으로 임의 전환하지 않는다. 실제 AI 생성·사용량 함수 수동 증가는 하지 않는다.

| 적용 후 기대 항목 | anon / authenticated | service_role |
|---|---|---|
| 3개 객체의 table_select/insert/update/delete | 모두 false | 모두 true |
| 3개 객체의 any_column_* | 모두 false | 권한에 따라 true |
| wk_courses.edit_token_select | false | true |
| wk_bump_usage EXECUTE | false | true |

추가로 `public_read_courses` 정책은 없어야 하고, wk_courses·wk_usage의 RLS는 true여야 한다. 뷰 RLS false와 edit_token 없는 객체의 null은 정상이다. 하나라도 예상과 다르면 운영 보안 완료로 판정하지 않는다.

**오류/복구:** SQL이 실패하면 트랜잭션 전체 롤백으로 이전 상태가 유지된다. 이는 기존 위험도 그대로라는 뜻이다. SQL 성공 후 앱 문제가 발견되면 서버 키/프로젝트/배포 버전과 필요한 서버 권한을 수정한다. `GRANT ... TO anon`이나 `USING(true)` 복원 SQL을 응급 처방으로 제공하지 않는다. 안전하게 복구할 수 없으면 코스 기능 일시 제한을 소유자와 결정한다. 이번 변경은 데이터를 삭제하지 않는다.

## 5. 기존 편집 토큰 처리 — 별도 승인 필요

DB 직접 읽기를 막아도 **이미 복사됐을 가능성이 있는 기존 편집 토큰은 자동 무효화되지 않는다.** 외부 조회 이력이 없거나 수집되지 않았다는 것만으로 안전을 증명할 수 없다. 소유자는 가능한 접근 로그/기간/변조 여부를 검토하고, 권한 차단과 별도로 기존 토큰 폐기 범위를 결정해야 한다.

토큰을 폐기하면 해당 토큰만 보유한 비로그인 생성자는 기존 코스 편집 권한을 잃을 수 있다. 로그인만으로 모든 편집 권한이 자동 복구되는 구조도 아니다. 필요하면 소유권 복구 절차를 먼저 설계한다. 공유 조회 링크는 토큰과 별개라 유지할 수 있다. **이번에는 토큰을 읽거나 교체하지 않았고 폐기 SQL도 실행하지 않았다.**

## 6. 남은 범위

- 운영 서버 키 존재는 사용자 확인을 받았고, 사용자 SQL 실행 후 목표 권한 상태도 확인했다. 실제 서버 키의 프로젝트 일치/배포 버전·공유 조회/내 코스/편집 기능 확인, 기존 토큰 폐기 결정은 남아 있다.
- 다른 테이블·의존 뷰·SECURITY DEFINER 함수·스토리지·기본 권한 전체는 별도 감사 범위. 이 세 객체와 한 함수 점검을 Supabase 전체 보안 완료로 표현하지 않는다.
- `checkAndBumpUsage()`의 DB 오류 시 호출 허용(fail-open)은 기존 정책대로 남았다. 서버 키 검증을 추가했다고 AI 비용 상한까지 강제 보장되는 것은 아니다. 운영 키 확인이 선행되어야 하며 비용/가용성 정책 변경은 별도 검토 대상이다.
- Gemini 9/10 429 이후 실호출 미재개. 신규 AI 생성→iPhone 17 저장·공유 종단간 검사와 제출용 실데이터 증빙은 남아 있다.
- 운영 DB 권한 변경은 사용자가 실행하고 사후 메타데이터를 제공했다. 에이전트의 운영 DB 쓰기·커밋·푸시·배포·토큰 교체는 미실행. DB 권한 확인을 실제 앱 동작·기존 토큰 무효화·배포 승인으로 확대 해석하지 않는다.
