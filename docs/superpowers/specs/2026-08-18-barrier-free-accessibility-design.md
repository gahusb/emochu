## 1. 왜 이걸 하는가

역대 수상작을 조사한 결과가 이 설계의 출발점이다.

| 연도 | 수상작 | 성격 |
|---|---|---|
| 2019 대상 | 찜 | 로컬 경험 공유 |
| 2021 대상 | 슈잉 | 관광 스팟 순위 |
| 2022 대상 | JOYRIDE | 자전거 여행 + 두루누비 결합 |
| 2023 우수 | DIB | **스쿠버다이빙** 특화 |
| 2024 최우수 | 또 강릉 | AR + **강릉 단일 지역** |
| 2024 발굴 | 싸이클로라마 / 그레킹 | 자전거 / 등산 |

**범용 여행 추천으로 대상을 받은 사례가 없다.** 2023 우수상 수상자는 성공 요인을 이렇게 밝혔다 — *"MZ세대 같은 일반적 타겟이 아닌 스쿠버다이버라는 뚜렷한 사용자 정의"*, *"참신함이 아닌 실현 가능성과 논리성"*.

이모추의 현재 포지션은 **"전국 단위 범용 AI 코스 추천"** 으로, 매년 가장 많은 팀이 내는 카테고리다. 완성도(30점)는 이미 확보했지만 **기획력 30점의 '독창성'을 얻기 가장 불리한 자리**다.

### 왜 무장애인가 — 피벗이 아니라 완성

이모추는 **이미** 동반자별 추천(`solo`/`couple`/`family`/`friends`)과 편의시설 반영(주차·유아차·키즈·반려동물)을 핵심 기능으로 갖고 있다. 무장애는 그 축의 **빠진 절반**이다.

지역특화 재포지셔닝(가점 +2)을 택하지 않은 이유도 같다. 제안서에 *"전국 단위 / 지역특화 아니오"* 로 제출했으므로 번복은 일관성을 해치고, 전국 17개 시·도 데이터 활용이라는 현재 강점을 스스로 줄이게 된다.

### 심사 배점에 닿는 지점

| 심사 항목 | 배점 | 이 작업이 닿는 방식 |
|---|---|---|
| 서비스 기획력 | 30 | 뚜렷한 타겟 + 고령화 트렌드 + 사회적 가치 |
| 데이터 활용 적절성 | 20 | 11개 → 12개 + **별도 API 상품** 교차 활용(융복합 근거) |
| 서비스 발전성 | 20 | 배리어프리 정책 수요 · 지자체 연계 여지 |
| 서비스 완성도 | 30 | 이미 확보 (배포 완료) — 여기서 잃지 않는 것이 목표 |

## 2. 목표와 비목표

### 목표

1. 접근성 요구를 **동반자와 독립된 축**으로 도입한다
2. 무장애 여행 정보 API(상품ID 15101897)를 실호출해 코스 추천에 반영한다
3. 접근성 미선택 사용자의 경험은 **한 글자도 바뀌지 않는다**
4. 1차 심사자료(기능설명서 PDF · 이미지 4~6장)를 완성한다

### 비목표 (이번에 하지 않는다)

- 지역특화 재포지셔닝
- 다국어 등 Phase 5~8 로드맵
- `/loop` 스케줄 등록 (박재오 미선택)
- `areaCode2`·`categoryCode2` 정적 코드표 마이그레이션 (별도 트랙)
- 운영계정 신청 (개발계정 1,000/일로 충분)

## 3. 선행 조건 — 사람만 할 수 있는 일

**[data.go.kr/data/15101897](https://www.data.go.kr/data/15101897/openapi.do) 활용신청 (개발단계 = 자동승인).**

🔴 **기존 `TOUR_API_KEY`와 같은 계정으로 신청**해야 키를 하나로 유지할 수 있다. 다른 계정으로 신청하면 환경변수가 둘로 갈라지고, 공모전 제출 시 인증키 제출 항목도 복잡해진다.

이것이 끝나기 전에는 M1 이후가 전부 막힌다.

## 4. 🔴 알려지지 않은 것 — 설계의 최대 리스크

2026-07-31 조사(`docs/tour-api-barrier-free-discovery.md`)에서 **단 한 번도 200 응답을 받지 못했다.** 전부 403 Forbidden이었다.

따라서 아래는 **전부 미확정**이다:

- 정확한 오퍼레이션명 (`detailWithTour2`가 유력 후보일 뿐)
- 파라미터 이름과 필수 여부
- 응답 필드명 (`data.go.kr` 문서상 "휠체어 접근성·점자블록·장애인화장실·보조견"이라는 **한글 설명만** 확인됨. 실제 JSON 키는 모름)
- 무장애 정보가 없는 콘텐츠의 응답 형태 (빈 items인지, 빈 문자열 필드인지)

**그래서 M0(탐침)이 독립 마일스톤으로 선행한다.** M0 결과에 따라 이 문서의 5~7장은 수정될 수 있다. 추측한 필드명으로 코드를 먼저 쓰지 않는다.

## 5. 아키텍처

```
lib/barrier-free-api.ts          [신규] KorWithService2 클라이언트
  ├ 위치기반 무장애 관광정보 조회   → 후보 수집 단계에서 교차 대조
  └ 상세 무장애 정보 조회          → 휠체어·점자블록·장애인화장실·보조견

lib/weekend-types.ts             AccessibilityNeed 타입 + FacilityInfo 확장
lib/weekend-ai.ts                하드 필터 + Gemini 제약 조건
app/components/course/wizard/
  steps/StepAccessibility.tsx    [신규] 선택적 스텝
app/components/FacilityBadges.tsx  무장애 뱃지 확장
```

### 5.1 왜 별도 파일인가

`lib/tour-api.ts`는 `BASE_URL`이 `KorService2`로 고정된 단일 상품 클라이언트다(`lib/tour-api.ts:5`). 무장애는 **서비스ID가 다른 별개 상품**(`KorWithService2`)이므로 같은 파일에 섞으면 `callTourApi`의 전제가 깨진다. 파일을 나눠야 "두 상품을 교차 활용한다"는 구조가 코드에도 드러난다.

### 5.2 타입 설계 *(2026-08-18 M0 실측으로 전면 수정)*

> 초판은 응답 필드를 4개 boolean 으로 가정했다. **실제로는 29개이고 값은 자유 텍스트다.** 아래는 실측(`docs/tour-api-barrier-free-discovery.md`) 반영본이다.

```ts
// 동반자와 직교한다. 데이터가 실제로 나뉘는 4그룹과 1:1로 맞춘다 —
// 데이터에 없는 구분을 UI 에 만들면 고를 수는 있는데 반영은 안 되는 선택지가 생긴다.
export type AccessibilityNeed = 'mobility' | 'visual' | 'hearing' | 'infant';

export const ACCESSIBILITY_LABELS: Record<AccessibilityNeed, string> = {
  mobility: '휠체어·보행 불편',
  visual: '시각장애',
  hearing: '청각장애',
  infant: '영유아 동반',
};

export interface BarrierFreeInfo {
  /** 원문 텍스트를 보존한다. 빈 문자열 필드는 담지 않는다. */
  details: Record<string, string>;
  /** 그룹별 정보 유무. undefined = 미확인 (3-state 유지) */
  mobility?: boolean;
  visual?: boolean;
  hearing?: boolean;
  infant?: boolean;
}
```

`CourseRequest` 에 `accessibility?: AccessibilityNeed[]`, `FacilityInfo` 에 `barrierFree?: BarrierFreeInfo` 를 **선택적으로** 추가한다.

**왜 텍스트를 보존하는가.** `"주출입구는 경사로가 있어 휠체어 접근 가능함"` 을 `true` 로 접으면 사용자에게 가장 쓸모 있는 문장을 버리게 된다. 뱃지 `✅ 휠체어 접근` 보다 원문이 낫고, 심사에서도 데이터 활용 깊이로 읽힌다.

### 5.3 🔴 `wheelchair` 필드의 함정

```
경복궁  wheelchair : "대여가능"                              ← 휠체어를 빌려준다
        exit       : "주출입구는 경사로가 있어 휠체어 접근 가능함"  ← 휠체어로 갈 수 있다
문화시설 route      : "경사로 이용 가능"
```

**`wheelchair` 는 접근성이 아니라 대여 서비스다.** 이름만 보고 접근성 판정에 쓰면 "휠체어를 빌려주는 곳"과 "휠체어로 갈 수 있는 곳"을 혼동한다. 실측에서도 `wheelchair` 는 관광지 10곳 중 1곳뿐인 반면 `route`·`exit` 은 모든 타입에서 상위였다.

→ **접근성 판정 근거는 `route`·`exit`·`elevator`·`restroom`·`parking` 이다.** `wheelchair` 는 `details` 에만 담아 표시한다.

### 5.4 그룹별 판정 필드

| 그룹 | 판정에 쓰는 필드 |
|---|---|
| `mobility` | `route` `exit` `elevator` `restroom` `parking` `room` `auditorium` `handicapetc` |
| `visual` | `braileblock` `audioguide` `bigprint` `brailepromotion` `guidesystem` `guidehuman` `blindhandicapetc` |
| `hearing` | `signguide` `videoguide` `hearingroom` `hearinghandicapetc` |
| `infant` | `stroller` `lactationroom` `babysparechair` `infantsfamilyetc` |

그룹 안의 필드 중 **하나라도 비어 있지 않으면** 그 그룹은 `true` 다. 한 곳도 없으면 `undefined`(미확인)이며 `false` 는 만들지 않는다 — API 는 "없음"과 "조사 안 됨"을 구분해 주지 않으므로, 없다고 단정할 근거가 없다.

## 6. 핵심 설계 판단 — 3가지

### 6.1 하드 필터다, 가중치가 아니다

휠체어가 필요한 사용자에게 *"점수는 높지만 계단만 있는 곳"* 을 추천하면 서비스가 무의미하다. 기존 스코어링은 취향·감정·날씨를 **가중치**로 다루지만, 접근성은 **충족하거나 못 하거나**다.

### 6.2 "미확인"을 "접근 가능"으로 표시하지 않는다

이것이 이 설계에서 가장 중요한 결정이다.

무장애 정보가 없는 장소를 접근 가능한 것처럼 보여주면, 그 정보를 믿고 이동한 사용자가 현장에서 돌아서야 한다. **데이터가 없다는 사실 자체를 정직하게 표시한다.**

| 상태 | 처리 |
|---|---|
| 확인됨 (접근 가능) | 상위 노출 + ✅ 뱃지 |
| 확인됨 (접근 불가) | 후보에서 제외 |
| **미확인** | 후순위 + **"무장애 정보 미확인" 뱃지** — 제외하지 않는다 |

미확인을 통째로 제외하면 결과가 0개가 되는 지역이 생긴다. 빈 화면보다는 *"확인된 곳 2곳, 정보 없는 곳 3곳"* 이 사용자에게 쓸모 있다.

### 6.3 미선택 시 완전 무영향

`accessibility`가 `undefined`이거나 빈 배열이면 **무장애 API를 호출조차 하지 않는다.** 기존 코스 생성 경로에 지연이나 동작 변화가 0이어야 한다. 회귀 테스트로 고정한다.

## 7. 실패 처리

무장애 API는 **부가 데이터**다. 그것 때문에 코스 생성 전체가 실패하면 안 된다.

| 상황 | 처리 |
|---|---|
| API 타임아웃 | 기존 `enrich` 단계와 동일하게 8초 가드. 초과 시 전부 "미확인" 처리 후 진행 |
| 403 (활용신청 미승인) | 서버 로그에 1회 경고. 사용자에게는 "미확인"으로 표시하고 코스는 정상 생성 |
| 일부 장소만 실패 | 해당 장소만 "미확인". 나머지는 정상 |
| 1,000/일 초과 | 429 예상. 위와 동일하게 degrade |

🔴 **인증키가 로그·응답에 새지 않아야 한다.** `lib/tour-api.ts`의 기존 마스킹 관례를 그대로 따른다.

## 9. 테스트 전략

현재 기준선은 **61개**(`loops/release-green/gate.mjs`의 `BASELINE`). 이 숫자는 회귀 감시에 쓰이므로, 테스트가 늘면 **기준선도 함께 올려야 한다.**

| 대상 | 테스트 |
|---|---|
| `barrier-free-api.ts` | 응답 파싱 · 403/타임아웃 degrade · 키 마스킹 |
| 하드 필터 | 접근 불가 장소 제외 · **미확인은 제외하지 않음** |
| 회귀 | **`accessibility` 미선택 시 기존 결과와 완전 동일** |

마지막 항목이 가장 중요하다. 이 기능은 기존 사용자에게 보이지 않아야 한다.

## 10. 하네스 연쇄 갱신 — 놓치면 조용히 깨지는 곳

이 작업은 "11개 API"라는 숫자에 의존하는 곳들을 건드린다. 코드만 고치고 아래를 빠뜨리면 Loop가 **잘못된 판정**을 내기 시작한다.

| 위치 | 현재 값 | 언제 바꾸나 |
|---|---|---|
| `loops/release-green/gate.mjs` — `BASELINE` | `61` | 테스트가 늘어난 **직후**. 안 올리면 회귀 감시가 헐거워진다 |
| `loops/submission-check/check.mjs` — `EXPECTED_APIS` | 11개 이름 집합 | 제출 서류의 활용 API 개수를 바꾸는 시점에 **함께** |
| `docs/2026-contest-info.md` — "TourAPI 활용 개수 11개" | 11 | 위와 동시에 |
| `CLAUDE.md` — TourAPI 활용 현황 표 | 11개 | 위와 동시에 |

⚠️ `checkApiList`는 **`lib/tour-api.ts` 한 파일만** 스캔한다. 새 클라이언트를 `lib/barrier-free-api.ts`로 분리하므로 **당장은 깨지지 않는다** — 그래서 더 위험하다. 조용히 "11개 일치 ✅"를 유지하면서 실제 제출 서류와 어긋날 수 있다.

판단: 무장애 API는 `KorService2`의 12번째 오퍼레이션이 **아니라 별개 상품**이므로, 제출 서류에는 *"KorService2 11개 + 무장애 여행 정보 1개 상품"* 으로 **구분해서** 적는 편이 정확하다. `EXPECTED_APIS`는 KorService2 11개 그대로 두고, 무장애는 별도 검사 항목으로 추가하는 쪽이 검사기의 의미를 지킨다.

## 11. 열린 질문

1. **M0 결과에 따라 5~7장이 바뀔 수 있다.** 특히 응답 필드명은 전부 추정이다.
2. 무장애 API의 "위치기반 관광정보"가 `KorService2`의 `locationBasedList2`와 **같은 contentId 체계**를 쓰는지 미확인. 다르면 교차 대조가 불가능해 설계를 다시 짜야 한다. → M0에서 반드시 확인할 것.
3. 기능설명서 PDF의 **지정 양식**을 아직 받지 못했다. 한국관광콘텐츠랩에서 다운로드 필요(임의 양식은 심사 제외).
