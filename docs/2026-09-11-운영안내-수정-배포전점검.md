## 3. 배포 전 발견한 보안 위험 — 당시 운영 상태 미확인

**후속 9/11 22:05:** 사용자가 운영 권한 점검 결과를 제공해 공개 SELECT 정책과 편집 토큰 SELECT 허용 구성을 확인했다. [DB 권한 보완 적용안](2026-09-11-DB-권한-보완-적용안.md)에 017·서버 키 검증·격리 SQL 14개 및 516 tests GREEN 결과를 기록했다. 아래는 최초 조사 시점의 기록이며, 실제 외부 유출·운영 수정 완료를 뜻하지 않는다.

저장소의 `012_enable_rls_wk_courses.sql`은 코스 테이블에 공개 SELECT 정책을 만들고, `014_course_edit_token.sql`은 같은 테이블에 `edit_token` 컬럼을 추가한다. 015·016도 공개 SELECT 정책을 유지한다고 명시한다. 014는 안전한 컬럼만 뽑은 뷰를 만들지만 원본 테이블의 SELECT 권한을 회수하지 않는다.

공유 조회 Next API는 edit_token을 조회·응답에서 제외하고 있다. 그러나 **운영 DB에 원본 테이블/컬럼 SELECT 권한과 허용 RLS 정책이 함께 남아 있다면**, 클라이언트의 DB 직접 조회는 Next API를 거치지 않을 수 있다. 편집 토큰 노출은 편집 권한의 신뢰를 무너뜨릴 수 있으므로 배포 전 확인 대상으로 올렸다. **실제 토큰 유출·악용을 확인했다는 뜻은 아니다.**

Supabase의 객체 권한과 RLS는 별도 계층이며, 안전한 API 응답이나 뷰 하나만으로 다른 조회 경로가 닫혔다고 볼 수 없다. [공식 설명](https://supabase.com/docs/guides/api/securing-your-api)

준비한 [읽기 전용 권한 점검문](../scripts/check-course-access.sql)은 다음 메타데이터만 조회한다.

- 대상 테이블/뷰 존재, 컬럼 이름, RLS 활성 상태
- anon/authenticated/service_role의 테이블 권한과 edit_token 컬럼 SELECT 권한
- 코스·사용량 테이블의 RLS 정책

코스·사용자 행이나 토큰 값은 읽지 않으며 DDL/DML·RPC 호출도 없다. PostgreSQL 권한 조회 함수는 [공식 문서](https://www.postgresql.org/docs/current/functions-info.html)에 따른다. SQL 파일은 **작성·내용 검토만 했으며 실제 PostgreSQL 실행 검증은 미수행**이다. 결과의 null은 ‘접근 차단’으로 읽지 않는다. 전체 DB 보안 감사나 모든 RPC/뷰 의존 경로 검사는 아니다.

현재 `lib/supabase/admin.ts`에는 서비스롤 키 누락 시 anon 키로 대체하는 동작도 있다. 따라서 직접 조회를 제한할 때 서버 키 누락을 익명 권한 확대로 우회해서는 안 된다. 현재 브라우저의 Supabase 사용은 인증 경로이고, 코스 DB 작업은 서버 admin 클라이언트 경로임을 소스에서 확인했다. 운영 서버 설정은 별도 확인이 필요하다.

## 4. 배포 준비물과 다음 단계

[배포 체크리스트](weekend-deploy-checklist.md)를 현재 코드에 맞춰 다시 작성했다. 옛 /weekend 경로, 테이블 삭제 권장, 익명 INSERT 허용, 무료 한도 단정, 연속 4회 생성 검사 안내를 제거했다. 데이터는 삭제하지 않았다.

현재 폴더에는 `.vercel/project.json`이 없고 `vercel` CLI 명령도 없다. Git은 main이며 HEAD는 `5269e3f`다. 이는 Git 연동 배포가 없다는 증거가 아니다. 누적 미커밋 변경이 많으므로 현재 로컬 코드가 운영 코드와 같다고 가정하거나 전체를 무검토로 게시하지 않는다. Production 브랜치 커밋은 자동 배포를 유발할 수 있으므로 대상·범위 확인이 먼저다. [Vercel 공식 안내](https://vercel.com/docs/git)

다음 진행에 필요한 것:

1. 운영 DB 소유자가 `scripts/check-course-access.sql`을 검토·실행한 **메타데이터 결과**를 제공한다. API 키나 실제 토큰 값은 필요 없다. 가능하면 SQL Editor 결과를 텍스트로 전달한다.
2. 권한 위험이 확인되면 공유 조회·내 코스·편집 기능의 영향 범위를 검토해 제한 마이그레이션을 준비하고, 별도 승인 후 적용한다. 토큰 회전도 실제 노출 여부와 영향 확인 후 결정한다.
3. Vercel 프로젝트·Production 브랜치·되돌릴 배포·누적 변경 범위를 확인하고 배포 승인을 받는다.
4. 새 배포에서 안내 문구·버튼 크기·viewport를 재확인한다. Gemini 한도 확인 뒤에만 AI 신규 생성과 iPhone 저장·공유 검증을 진행한다.

**로컬 게이트 GREEN과 운영 배포 승인 여부는 별개다.** 이번에는 보안 점검 결과와 배포 연결 정보가 없어 운영 게시 단계로 넘어가지 않았다.
