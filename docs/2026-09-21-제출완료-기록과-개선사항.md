> 이모추!는 한국관광공사 관광정보를 활용해 주말 나들이 코스를 제안하는 웹 서비스입니다. 목적지·기분·여행 시간·방문 요일·동반자·취향을 4단계로 선택하면 관광지·맛집·카페·문화시설·축제 후보를 모아 점수화하고, AI가 시간표와 이동 동선, 장소 설명을 갖춘 코스를 만듭니다. 방문일의 정기 휴무·운영시간·날씨를 대조해 확인되지 않은 항목은 '확인 필요'로 표시하며, 무장애 여행 정보를 연동해 접근성 조건에 맞는 장소를 우선합니다. 장소 교체와 링크 공유를 지원합니다.

## 2. 제출 절차 지식 (10/28 발표심사 때 또 필요함)

### 접수 경로 — 마이페이지가 아니다

```
콘텐츠랩 로그인 → 「공모전」 > 「접수확인」
  → 목록에서 '팀명' 또는 '서비스명' 클릭
  → 이메일 인증(이메일 발송 → 인증번호 입력 → 확인)
  → 안내 메시지 '확인'
  → 접수확인 상세화면 하단 「심사자료 제출」 버튼
```

- ⚠️ 목록의 **「제출일자」는 참가신청서를 낸 날**(이모추 = 2026-05-06)이라 1차 심사자료와 무관하다. 볼 곳은 **「진행상태」** 칸. 이것 때문에 제출처를 못 찾고 헤맸다.
- ⚠️ **「심사자료 제출」 버튼은 이메일 인증을 통과해야 나타난다.**
- 인증번호는 콘텐츠랩 등록 이메일로 발송되며, 그 주소는 투어라즈(`touraz.kr`) 마이페이지 > 내 프로필 관리에서 확인·수정.
- 제출 완료 시 안내 메일 발송. **기간 내 무제한 수정 가능**, 기간 종료 후 수정 불가.

### 인증키 함정

```
data.go.kr 로그인 → 마이페이지 → 첫 화면 최하단 「개인 API 인증키」
  → [인증키 복사(Encoding)] · [인증키 복사(Decoding)] 버튼 2개
```

> 공식 매뉴얼 경고: *"[마이페이지 > 데이터 활용 > Open API > 인증키 발급현황] 메뉴에서는 **인코딩키만 확인 가능**하므로 … 인코딩키와 디코딩키를 모두 확인하여 제출해주세요."*

평소 키를 찾던 메뉴로 가면 하나만 보여서 누락하기 쉽다.

### 기타

- 입력 7번 **「활용 OpenAPI 서비스」는 자유 입력이 아니라 목록 선택**이다(1건 이상 필수, 미선택 시 심사 제외).
- 공식 매뉴얼 2종 원본은 옵시디언 볼트 `raw/2026-09-21-관광데이터공모전-*.pdf` 에 스냅샷 보존(Drive 링크 링크로트 대비).

## 4. 개선 후보 (다음 작업자용)

> ✅ **2026-09-21 13:35 처리됨(로컬 전용·미배포).** P2·P4·P5·P6·P7 완료, P1 절반(계측만·표본 0건), P3 잠정(가족 한정 12km).
> 무엇을 했고 **무엇을 안 했는지**는 `docs/2026-09-21-제출후-개선-작업결과.md` 에 있다. 아래 원문은 당시 관찰 기록으로 남긴다.

> 🟡 **전부 「관찰」이지 「측정」이 아니다.** 한 가지 조건 조합으로 2회 생성한 결과라 표본이 좁다. 우선순위는 **10/28 발표심사 배점**(적정성 30 / 완성도 30 / **실용성 25** / 발표 15) 기준으로 매겼다.

### 🔴 P1 — 코스 생성 대기 시간

- **관찰**: 「코스 만들기」 클릭 후 **20초 시점에도 여전히 "코스를 설계하고 있어요"** 였고, **45초 이내에 완료**됐다. 2회 모두 비슷했다.
- **왜 중요한가**: 심사위원이 직접 써볼 때 **첫 인상이 40초 대기**가 된다. `maxDuration=60`이라 최악엔 타임아웃 폴백까지 간다. **완성도·실용성 두 배점에 동시에 걸린다.**
- **제안**: 결과를 빠르게 하는 것보다 **기다리는 동안 무엇이 일어나는지 보여주는 쪽**이 비용 대비 효과가 클 수 있다 — 현재 로딩은 문구 하나뿐이다. 단계 표시(후보 수집 → 상세 보강 → 코스 구성 → 검증)는 이미 엔진이 그 순서로 도니 상태만 흘려보내면 된다.
- 🟡 미측정: 실제 구간별 소요(어디서 오래 걸리는지), 한도(429) 상황에서의 분포.

### 🔴 P2 — 홈 카드 배지 「공연」 오표기 (원인 확인됨)

- **관찰**: 홈 화면 추천 카드 4장(**세종문화회관 · 교보문고 · 신문박물관 · 이화여고100주년기념관**)의 배지가 **전부 「공연」** 이었다.
- **원인 (코드로 확인)**: `app/components/SpotCard.tsx:31` 이 중분류 **`A0206` 을 통째로 `label: '공연'`** 으로 매핑한다. `lib/tour-api.ts:430` 도 같은 코드를 `'공연장'` 으로 쓴다.
  그런데 **`A0206` 은 「문화시설」이다** — 이 레포의 설계 문서 `docs/weekend-app-design.md:526` 에 `cats: ['A02', 'A0206'], // 인문관광, 문화시설` 로 명시돼 있다.
  즉 **박물관·도서관·미술관·기념관이 전부 「공연」으로 표시된다.** 공연장은 `A0206` 의 **소분류 하나**일 뿐이다.
- **문제**: 교보문고(도서관/서점)·신문박물관이 「공연」으로 뜬다. **첫 화면에서 데이터 활용의 정확도를 의심받는 지점**이고, 데이터 활용 배점(1차 20점)과 직결된다.
- **제안**: `A0206` 의 라벨을 **「문화시설」** 로 고치고, 진짜 공연은 소분류(`A02060500` 등)나 `contentTypeId=15`(행사/공연/축제)로 구분한다.
  🟡 단 `lib/weekend-ai.ts:415-417` 의 `boostCat3` 가 `A0206xx` 소분류를 직접 쓰고 있으니, 라벨만 바꿔도 스코어링에는 영향이 없는지 확인할 것.

### 🟡 P3 — 동선 거리

- **관찰**: 생성된 코스에 **차로 37분(12.5km)** 구간이 있었다(매헌시민의 숲 → 강남). 총 이동 14.3km / 20.0km.
- 코스 자체는 성립하지만, 「가족+아이 / 하루」 조건에서 한 구간이 37분이면 체감이 나쁘다. 기존 `docs/2026-09-09-식사-동선-보완-결과.md`의 후속으로 볼 여지가 있다.
- 🟡 직선거리 기반 추정치라 실제 도로 경로와 다르다는 점은 기존 문서에 이미 명시돼 있다.

### 🟡 P4 — 장소 교체 후보 로딩

- **관찰**: 「바꾸기」 클릭 후 **"주변을 찾는 중…"** 상태가 잠시 유지됐다(1.5초 시점 캡처에 로딩 중으로 잡힘).
- 기능은 정상이고 곧 후보가 채워진다. 다만 **제출 이미지 촬영 때 로딩 화면이 찍힐 정도**였으니, 시연·촬영 시 주의.

### 🟡 P5 — 첫 방문 위치 권한 배너

- **관찰**: 첫 진입 시 하단에 *"내 주변 주말 코스를 추천받아 보세요 / 위치 허용 / 서울로 볼게요"* 배너가 뜬다.
- 기능상 문제는 없으나 **화면 하단을 가린다.** 심사·시연 촬영 시 먼저 닫아야 깔끔하다.

### 🔵 P6 — `submission-check`의 API 개수 기준 불일치

- `submission.json`의 `api-list` 항목은 **11개(KorService2) 기준으로 검사**하는데, **제출 서류는 12개**(무장애 포함)로 적는다.
- 검사는 통과하지만 **검사 기준 ≠ 서류 문구**라 다음 사람이 헷갈린다. `CLAUDE.md` 의 「TourAPI 활용 현황」 절에 이미 *"서류에는 12개로 적는다"* 가 있으니, 검사 쪽 라벨에도 근거를 남기면 좋다.

### 🔵 P7 — `submission.json` 수동 4건 상태 갱신

- 팀정보·서비스정보·테스트계정·인증키 모두 **실제로는 제출 완료**인데 `done: false`다. `true`로 바꾸면 **10/10**.
- 🔴 **실제 인증키 값은 절대 이 파일에 적지 않는다**(git 추적 대상). 완료 표시만.
