## P1 — 코스 생성 대기 시간 (🟡 절반)

인수인계의 착수 순서 그대로 **측정부터** 했다. 다만 *측정기를 붙였을 뿐 표본은 아직 없다* — 표본을 뽑으려면
실제 생성(= Gemini + TourAPI 실호출)이 필요한데, **이번 세션은 외부 호출을 하지 않았다.**

**붙인 것** — `lib/course-stage-timer.ts` (신규) + `app/api/course/route.ts`

- 단계: `collect`(후보·날씨·축제·숙박) → `enrich`(detailIntro2) → `score` → `accessibility` → `ai` → `finalize` → `persist`
- 요청 하나가 **로그 한 줄**이다. 오래 걸린 단계가 앞에 온다:
  `[이모추API] 소요(ms) total=… ai=… collect=… enrich=… candidates=66 ai=gemini stops=6`
- `ai` 값으로 **경로**를 구분한다: `gemini` / `timeout_fallback`(53초 상한에 걸려 폴백) / `skipped`(수집만으로 이미 시간 초과)
- 🔑 **아무것도 건너뛰지 않는다.** 캐시로 때우면 인증키 호출 이력이 안 남아 심사에서 손해다(인수인계 「하지 말 것」).

**화면** — `lib/loading-messages.ts` · `CourseLoading` · `useCourseGeneration`

- 「평균 15~25초 소요」는 **사실과 달랐다**(실측 20초 시점 생성 중, 45초 내 완료). → `보통 30초 안팎, 길면 1분까지 걸려요`
- 흘러간 시간을 말한다: `12초째 만드는 중`. 45초를 넘기면 `예상보다 오래 걸리고 있어요. 1분까지는 기다려볼게요`
- 진행 막대는 **「예상」**이라고 적고 95%에서 멈춘다.

🔴 **단계 표시(「후보 수집 중 → 코스 구성 중」)는 넣지 않았다.** 지금 API 는 단일 POST 라
클라이언트가 **어느 단계인지 알 방법이 없다.** 모르는 것을 아는 척하면 로딩 멘트의 첫 번째 규칙
(*거짓말하지 않는다*)을 어긴다. 진짜 단계 표시는 **① 계측 표본으로 어디가 지배적인지 확인한 뒤
② 스트리밍(NDJSON/SSE)으로 단계를 흘려보내는** 순서가 맞다.
